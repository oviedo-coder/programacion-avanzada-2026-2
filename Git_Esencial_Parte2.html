🌿 ¿Qué es una rama?

Una rama es una línea de desarrollo independiente. La rama principal casi siempre se llama main. Trabajar en una rama aparte les permite avanzar en algo (una funcionalidad, un experimento) sin afectar el código que ya funciona en main, hasta que estén seguros de que está listo.

git checkout -b feature/mi-funcionalidad   # crea la rama y te mueve a ella
git add .
git commit -m "feat: avance de mi funcionalidad"
git checkout main
git merge feature/mi-funcionalidad         # trae los cambios a main
git push

🔁 Flujo completo: crear, trabajar, subir y fusionar

Aquí está el proceso completo, paso a paso, desde que crean la rama hasta que su código ya quedó integrado en main para siempre.

1. Crear la rama

Antes de empezar algo nuevo, asegúrense de partir de la versión más reciente de main:

git checkout main
git pull                                # traen lo último antes de ramificar
git checkout -b feature/registrar-compra

2. Trabajar y hacer commits en la rama

Programan normal, y van guardando avances con commits pequeños y frecuentes — no uno solo gigante al final:

git add .
git commit -m "feat: valida que no exista una compra duplicada"
# ... siguen trabajando ...
git add .
git commit -m "feat: implementa el método confirmar()"

3. Subir la rama al repositorio remoto

La primera vez que suben esa rama, usan -u (de "upstream") para conectarla con GitHub:

git push -u origin feature/registrar-compra

De ahí en adelante, mientras sigan en esa misma rama, basta con git push a secas — Git ya sabe a dónde mandarlo.

4. Verificar que funciona antes de fusionar

Antes de mezclar con main, confirmen que su parte realmente funciona:

  • Corran el proyecto y prueben la funcionalidad manualmente.
  • Si ya tienen pruebas unitarias de esa parte, córranlas.
  • Si pueden, pídanle a un compañero que revise su código antes de fusionar (aunque sea informalmente, leyendo el diff en GitHub).

5. Fusionar a main, una vez verificado

git checkout main
git pull                                # traer lo que otros hayan fusionado mientras tanto
git merge feature/registrar-compra
git push

Si aparece un conflicto en el merge, resuélvanlo siguiendo el Problema 3 de esta guía, más abajo.

6. Borrar la rama ya fusionada (opcional, pero recomendado)

Una vez que su rama ya está integrada en main, no necesitan conservarla — borrarla mantiene el repositorio ordenado:

git branch -d feature/registrar-compra              # borra la rama local
git push origin --delete feature/registrar-compra   # borra la rama en GitHub
Resumen del ciclo completo pull en main → checkout -b → trabajar y commit → push -u origin → verificar → checkout main → pull → merge → push → borrar la rama.

🗂️ Ramas para el proyecto del semestre

Para su proyecto en grupo, usen esta convención de nombres — les va a evitar confusiones y les da algo profesional que mostrar en la sustentación:

  • feature/nombre-del-caso-de-uso — para una funcionalidad nueva, ej. feature/registrar-compra
  • fix/descripcion-corta — para corregir un error, ej. fix/validacion-precio-negativo
  • docs/descripcion-corta — para documentación, ej. docs/glosario-lenguaje-ubicuo

Regla de oro para el grupo: nadie trabaja directo sobre main a partir de ahora. Cada quien crea su rama para lo que le toque, y solo se fusiona a main cuando ya funciona.

Ejemplo de reparto en un grupo de 3 Persona A: feature/registrar-compra · Persona B: feature/publicar-producto · Persona C: feature/dejar-comentario — cada uno en su propia rama, fusionando a main cuando su parte esté lista y probada.

🗺️ Ejemplos: distintas formas de organizar su repo

No hay una única forma "correcta" de repartir las ramas — depende de cómo trabaje su grupo. Aquí tienen 3 ejemplos reales para que vean las opciones y elijan la que mejor les quede.

Opción 1 — Por caso de uso (la más recomendada para este proyecto)

Cada rama representa una funcionalidad completa del negocio, sin importar quién la haga.

main
feature/registrar-compra
feature/publicar-producto
feature/dejar-comentario
feature/solicitar-reembolso

✅ Ventaja: en la sustentación pueden mostrar "esta rama es el caso de uso X", clarísimo para explicar. ✅ Encaja perfecto con cómo van a ir armando los Casos de Uso guía por guía.

Opción 2 — Por integrante del grupo

Cada persona tiene su propia rama de trabajo general, y ahí va avanzando lo que le toque esa semana.

main
feature/juan
feature/maria
feature/andres

⚠️ Funciona, pero es menos clara para la sustentación — si alguien pregunta "¿qué hay en feature/juan?", la respuesta es "depende de la semana", no una funcionalidad concreta.

Opción 3 — Por capa técnica

Una rama para todo el trabajo de backend, otra para todo el frontend.

main
feature/backend-dominio
feature/frontend-angular

⚠️ Útil solo si el grupo se dividió tajantemente en "los del backend" y "los del frontend" — para este curso, donde todos deben entender ambas partes, no es la más recomendable.

Recomendación Usen la Opción 1 (por caso de uso) como base — es la que mejor refleja cómo van a construir el proyecto guía por guía, y la más fácil de explicar en la sustentación final.
problema 1

"fatal: not a git repository"

Cuándo aparece: al correr cualquier comando git estando fuera de la carpeta del repositorio.

fatal: not a git repository (or any of the parent directories): .git
Solución 
pwd                     # confirma dónde estás
cd ruta/a/tu/repo       # ubícate dentro del repo
git status              # ahora sí funciona
problema 2

Rechazado por "fetch first" / "non-fast-forward"

Cuándo aparece: intentas hacer push, pero alguien más ya subió cambios a esa misma rama antes que tú.

! [rejected] main -> main (fetch first) error: failed to push some refs
Solución 
git pull                # trae los cambios de tu compañero primero
git push                # ahora sí sube los tuyos
Si al hacer pull aparece un conflicto, pasa al Problema 3.
problema 3

Conflicto de merge

Cuándo aparece: dos personas modificaron la misma línea del mismo archivo.

Git marca el archivo así:

<<<<<<< HEAD
tu código
=======
el código de tu compañero
>>>>>>> feature/rama-de-tu-compañero
Solución
  1. Abre el archivo, decide qué código dejar (el tuyo, el de tu compañero, o una combinación de ambos).
  2. Borra las líneas <<<<<<<, ======= y >>>>>>>.
  3. Guarda, y termina el merge:
git add archivo-con-conflicto.java
git commit -m "fix: resuelve conflicto de merge"
Habla con tu compañero antes de resolverlo solo — muchas veces la mejor solución es combinar ambas partes.
problema 4

Hice commit en la rama equivocada

Cuándo aparece: olvidaste crear tu rama y trabajaste directo sobre main, o sobre la rama de otra persona.

Solución (si el commit AÚN NO se subió con push) 
git branch feature/mi-rama-correcta   # crea la rama en el punto actual
git reset --hard HEAD~1               # regresa main a como estaba antes
git checkout feature/mi-rama-correcta # tu commit está a salvo aquí
Si ya hiciste push a la rama equivocada Avísale a tu docente o a tu equipo antes de forzar cambios — mover commits que otros ya vieron puede generar más confusión que dejarlo así y seguir desde ahí.
problema 5

Quiero deshacer mi último commit

Si el commit es solo local (no le has hecho push) 
git reset --soft HEAD~1   # deshace el commit, deja los cambios listos para repetirlo bien
Si ya le hiciste push y otros ya lo tienen 
git revert HEAD           # crea un commit nuevo que cancela el anterior, sin borrar historial

💡 revert es más seguro en equipo porque no reescribe el historial que otros ya descargaron.

problema 6

Subí algo que no debía (contraseñas, archivos generados)

Para que no vuelva a pasar Agrega un archivo .gitignore en la raíz del repo con lo que nunca debe subirse: 
.env
application-secrets.properties
/build/
/node_modules/
Si ya lo subiste por error Avísale a tu docente — si es una contraseña real, cámbiala de inmediato (el archivo queda en el historial aunque lo borres después, así que la contraseña ya debe considerarse expuesta).

📋 Cheatsheet de ramas

# Crear y moverte a una rama nueva
git checkout -b feature/nombre-caso-de-uso

# Ver en qué rama estás y cuáles existen
git branch

# Cambiar de rama
git checkout nombre-rama

# Traer los cambios de una rama a la actual
git merge nombre-rama

# Subir tu rama por primera vez
git push -u origin feature/nombre-caso-de-uso

# Borrar una rama que ya fusionaste
git branch -d nombre-rama
